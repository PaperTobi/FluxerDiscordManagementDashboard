# 0003 — Text-to-speech: Piper voices on rten, phonemes from espeak-ng (C) at Piper's commit

Date: 2026-10-04. Status: decided (internal detail, by the user's rule: fix in depth, else an alternative that follows
the ideology, else the closest one).

## What was needed
Speak warnings, greetings, action notices and "say now" texts in several languages (German and English built in, more
Piper voices installable), sounding as good as the old bot's Piper 1.8.0.

## Decision
- **Voice model**: Piper's VITS `.onnx` files run on **rten 0.27** (pure Rust). With both noise scales at 0 (the model
  is then deterministic) rten's audio equals onnxruntime's within 1.8e-4 (peaks 0.3–0.7) and with identical length,
  for de_DE-thorsten-{high,medium} and en_US-lessac-{high,medium}.
- **Phonemes**: **espeak-ng (C) at commit 724808c**, the exact commit piper-tts 1.8.0 builds, linked statically by
  `crates/pb-espeak` (built by `cargo xtask espeak-ng`), with Piper's own text handling ported line by line
  (`[[raw phonemes]]`, language-switch flags, clause punctuation, NFD, vowel clusters, ids). 686/686 test sentences give
  Piper's exact ids. Registered in docs/exceptions.toml.
- **Built-in voices**: de_DE-thorsten-high and en_US-lessac-high (pinned to rhasspy/piper-voices c10ece1a with their
  published sha256); any other Piper voice can be installed.

## Why not the pure-Rust espeak-ng port
espeak-ng 0.2.0 (pure Rust, GPL) gives Piper's ids for only 87/173 German and 109/170 English sentences: it always
skips multi-word dictionary entries (`has been` → one word in C), and differs in German r after consonants, compound
stress, `ë`, `s`/`z`, ordinals ("3." → "dritte") and domain names. Bringing a 16 000-line port to parity is not a
bounded fix; no other pure-Rust phonemizer uses espeak's phoneme set. The port is kept as a dev-only parity report
(`examples/port_parity.rs`) so the exception can be dropped when it catches up.

## Speed
Real-time factor (lower is faster), 2.2 s sentence, same machine:

| voice | rten 1 / 2 / 4 threads | onnxruntime 1 / 2 / 4 |
|---|---|---|
| thorsten-high | 0.77 / 0.40 / 0.21 | 0.46 / 0.24 / 0.13 |
| thorsten-medium | 0.10 / 0.06 / 0.03 | 0.06 / 0.04 / 0.02 |

93 % of rten's time is convolution (HiFi-GAN decoder); onnxruntime's MLAS kernels are faster. rten is still several
times faster than real time and warnings are pre-rendered and cached, so latency only shows for "say now" with new
text. onnxruntime (C++) is not needed.

Update 2026-10-04 (speed): most of that convolution time was not arithmetic. rten-gemm packs a convolution's input
for the matrix multiplication with a scalar gather, also where a unit-stride Conv1d reads consecutive samples, which
is nearly every convolution of the decoder; that packing was about 40 % of the `Conv` time. `third_party/rten-gemm`
(0.27.0 with one patch, see its PATCHES.md; a candidate upstream contribution for rten#1444) copies those rows
instead. The audio is bit for bit what it was (still within 1.81e-4 of onnxruntime). Median ms per sentence,
`bench tts` against the Python bot's piper-tts, 2 threads each, interleaved runs on the same machine (Ryzen 5 7600X,
load average 4–6 from other builds):

| voice | onnxruntime | rten before | rten now |
|---|---|---|---|
| en_US-lessac-medium | 102 | 165 | 100 |
| de_DE-thorsten-medium | 195 | 303 | 198 |
| en_US-lessac-high | 653 | 1180 | 783 |

With one thread each the gap to onnxruntime is 2–13 % (lessac-high 1365 against 1339 ms); the first sentence after
start (loading included) takes 157–846 ms against Python's 666–1297. What is left: the matrix multiplication itself
(about 75 % of the CPU's peak, as with onnxruntime's MLAS), the LeakyRelu that onnxruntime fuses into the convolution
before it, and rayon's idle workers giving their core away when other programs run (onnxruntime's pool spins).
`RTEN_TIMING="by-shape=1"` in the environment prints rten's time per operator and shape.
